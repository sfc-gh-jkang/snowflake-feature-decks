Four Modes, One Decision

The refresh mode is fixed at creation. Choosing it is the single most consequential decision in a dynamic table definition.

ADAPTIVE GA

Incremental by default; reinitializes automatically when Snowflake detects a bulk change. The documented preference for all incremental workloads.

INCREMENTAL

Processes only changed rows. Creation fails immediately if the definition is not incrementalizable.

FULL

Re-executes the whole definition every refresh. Always works. Predictable cost regardless of change volume.

AUTO default

Resolves once at creation to INCREMENTAL or FULL. Never resolves to ADAPTIVE. This is the trap.

The documented guidance is unusually direct: "Use ADAPTIVE refresh mode as your preferred refresh mode for all incremental workloads." And from the Snowflake engineering blog: "Never use REFRESH_MODE = AUTO in production." GA note Blog: What's new with Dynamic Tables

A fifth mode, CUSTOM_INCREMENTAL, lets you write the refresh logic yourself as MERGE or INSERT DML. It is in Public Preview and covered at the end.

-- Mode is set at creation. ALTER cannot change it.
CREATE OR REPLACE DYNAMIC TABLE dt_orders
  TARGET_LAG = '10 minutes'
  WAREHOUSE = transform_wh
  REFRESH_MODE = ADAPTIVE
AS
  SELECT order_id, customer_id, order_date, total_amount
  FROM raw_orders
  WHERE order_status = 'COMPLETED';

ADAPTIVE Refresh

Generally available since 2026-07-30. It solves the specific failure where one nightly bulk load makes incremental refresh cost more than a rebuild.

Reinitialization Triggers

Snowflake reinitializes when it judges an incremental refresh more expensive than a rebuild. Documented triggers:

INSERT OVERWRITE on a base tableReinitializes
Bulk delete / update, large row fractionReinitializes
Cortex AI functions, UDFs, external functionsUsually not
Projection / filter / sort onlyUsually not

Why the Exceptions Make Sense

Where the definition calls expensive per-row operators, re-executing them across every row costs more than the incremental path — so the heuristic declines to rebuild. Where the definition is trivially incrementalizable, there is nothing to gain.

The heuristic is comparing two real costs, not applying a row-count rule.

Reinitializations are observable, which matters because an unexplained cost spike is otherwise hard to attribute:

-- Did it reinitialize, and why?
SELECT NAME, REFRESH_ACTION, REINIT_REASON, REFRESH_START_TIME,
       DATEDIFF('second', REFRESH_START_TIME, REFRESH_END_TIME) AS DURATION_SEC
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(
             NAME_PREFIX => 'MY_DB.MY_SCHEMA.',
             DATA_TIMESTAMP_START => DATEADD('day', -7, CURRENT_TIMESTAMP())))
WHERE REFRESH_ACTION = 'REINITIALIZE'
ORDER BY REFRESH_START_TIME DESC;

ADAPTIVE carries the same requirements as INCREMENTAL: the definition must be incrementalizable, or creation fails. It also inherits the pipeline constraint on upstream full-refresh tables. To limit the cost of an occasional rebuild, pair it with a frozen region or a larger INITIALIZATION_WAREHOUSE. REFRESH_HISTORY Frozen regions

Diagnosis

The AUTO Trap

AUTO is the default when you omit REFRESH_MODE. It fails quietly in two distinct ways.

1. It Resolves Silently

With AUTO, an unsupported construct does not raise an error — creation succeeds and the table becomes FULL refresh. You are billed for full reprocessing on every cycle and nothing told you.

With REFRESH_MODE = INCREMENTAL the same definition fails loudly at create time, which is what you want.

2. It Resolves Only Once

AUTO evaluates the definition at creation and locks the result in. It never re-evaluates. If an upstream view is later modified so incremental is no longer possible, refreshes fail rather than quietly switching to full.

-- Fails immediately: EXCEPT is not incrementalizable.
CREATE OR REPLACE DYNAMIC TABLE dt_unsupported
  TARGET_LAG = '10 minutes' WAREHOUSE = transform_wh
  REFRESH_MODE = INCREMENTAL
AS SELECT order_id FROM raw_orders
   EXCEPT SELECT order_id FROM excluded_orders;

-- 002711 (0A000): SQL compilation error:
--   Dynamic Table 'DT_UNSUPPORTED' is defined with REFRESH_MODE = INCREMENTAL,
--   but the query is not supported for incremental refresh.

-- Same definition with AUTO: succeeds, silently becomes FULL.

Failing at create time is the feature. Set the mode explicitly in production so cost is a deliberate choice recorded in the DDL. Reserve AUTO for exploration, then lock the mode in before promoting. Refresh modes

CURRENT_TIMESTAMP() is worth calling out because the rule is positional, not absolute: timestamp functions are supported in WHERE, HAVING, and QUALIFY, and only break incremental when they appear in the SELECT list. A rolling time filter is fine; stamping a processed-at column is not. Supported queries

Some computations genuinely cannot be incrementalized. An exact median has to re-sort every value when one row arrives, and a set difference has to compare both full sets. These are not gaps in the implementation — there is no shortcut that inspects only the new rows.

Diagnosing a Full-Refresh Regression

Start with the resolved mode, not the DDL. What you asked for and what you got can differ.

-- 1. What mode is it actually running, and why?
SHOW DYNAMIC TABLES LIKE 'dt_orders';
-- inspect: refresh_mode, refresh_mode_reason

-- 2. Across a whole schema, find everything not running incrementally.
SELECT "name", "refresh_mode", "refresh_mode_reason", "target_lag"
FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()))
WHERE "refresh_mode" <> 'INCREMENTAL';

-- 3. Is refresh duration trending up? Compare average by action.
SELECT NAME, REFRESH_ACTION, COUNT(*) AS refreshes,
       ROUND(AVG(DATEDIFF('second', REFRESH_START_TIME, REFRESH_END_TIME))) AS avg_sec
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY(
             NAME_PREFIX => 'MY_DB.MY_SCHEMA.',
             DATA_TIMESTAMP_START => DATEADD('day', -14, CURRENT_TIMESTAMP())))
GROUP BY NAME, REFRESH_ACTION
ORDER BY avg_sec DESC;

Reading refresh_mode_reason

NULLIncremental is active — nothing wrong
QUERY_NOT_SUPPORTED_FOR_INCREMENTALFix the definition shape
USER_SPECIFIED_FULL_REFRESHDeliberate — someone set FULL
UPSTREAM_USES_FULL_REFRESHFix upstream, not this table

UPSTREAM_USES_FULL_REFRESH is the one people chase in the wrong place. The table you are looking at is fine; its parent is forcing the mode. Walk up the pipeline before touching the definition in front of you. Troubleshoot refreshes

Part 3

Design and Cost

The Five Percent Myth

The most common misconception about dynamic tables, and the docs now have a section dedicated to correcting it.

What People Believe

"If more than 5% of the base table changes, Snowflake automatically switches to full refresh."

This is false. There is no automatic switch.

What Actually Happens

Five percent is a performance guideline for when incremental works well. Snowflake never changes a dynamic table's configured refresh mode based on change volume.

Exceed it and incremental simply gets slower — and keeps running, at that cost, indefinitely.

Why this matters operationally: nothing will alert you. A table configured INCREMENTAL whose change rate has grown past the useful range will quietly cost more than FULL would, every cycle, until someone compares refresh durations. That comparison is the only signal.

Consistently high churn

Recreate with REFRESH_MODE = FULL.

Occasional bulk loads

Use ADAPTIVE — it rebuilds on the spike and resumes incremental after.

Heavy recurring deletes

FULL is often the right starting point; incremental must scan many files to find deleted rows.

Wholesale dimension reloads

Faster to rebuild than to diff. Start at FULL.

Pipeline Shape

Refresh mode is per-table, but one constraint propagates downstream.

The Constraint

An INCREMENTAL or ADAPTIVE table can sit downstream of a FULL-refresh table only when that upstream table has a system-derived unique key or a frozen region. Given either, Snowflake can compute row-level changes across full refreshes.

The Non-Obvious Part

In this scenario you must set REFRESH_MODE = INCREMENTAL explicitly on the downstream table. AUTO will not resolve to incremental here, so relying on the default silently costs you full refreshes down the chain.

An upstream FULL table does not otherwise force downstream tables to FULL — each table decides independently. Also note replication and cloning both reinitialize incremental tables: replicated tables reinitialize after failover before resuming, and clones may reinitialize on first refresh. Cost Controls

Two levers do most of the work: which warehouse absorbs a rebuild, and how often you ask for one.

-- Dual-warehouse strategy: size for the rebuild, not the steady state.
CREATE OR REPLACE DYNAMIC TABLE dt_orders
  TARGET_LAG = '10 minutes'
  WAREHOUSE = transform_wh_s              -- routine incremental refreshes
  INITIALIZATION_WAREHOUSE = transform_wh_xl  -- occasional reinitialization
  REFRESH_MODE = ADAPTIVE
AS
  SELECT order_id, customer_id, order_date, total_amount
  FROM raw_orders
  WHERE order_status = 'COMPLETED';

Split the Warehouses

Reinitialization is a full scan; routine incremental refresh is not. Sizing one warehouse for both means over-provisioning for the common case. The Snowflake blog recommends this split explicitly. Blog

Target Lag Is a Cost Dial

Lag sets how often refreshes trigger. Tightening it multiplies refresh count. Ask what freshness the consumer actually needs rather than defaulting low.

Mode Changes Are Not Free

ALTER cannot change refresh mode. CREATE OR REPLACE drops and recreates, reinitializing the table and every downstream dependency. Prefer CREATE OR ALTER. CREATE DYNAMIC TABLE

Split Stacked Operators

Definitions stacking GROUP BY, DISTINCT, and window functions can run slower incrementally than fully. Splitting into simpler chained tables often restores incremental efficiency. Refresh optimization

Custom Incrementalization

The escape hatch when a transformation is not expressible in a supported shape. Public Preview

What It Is

CUSTOM_INCREMENTAL lets you define refresh logic directly as MERGE or INSERT DML inside a REFRESH USING clause. Snowflake still owns scheduling, retries, and transactional guarantees; you own how changes land.

When to Reach for It

When a definition needs a construct that forces FULL but the workload genuinely needs incremental economics. It bypasses standard query analysis entirely — which is the point, and also the risk.

Bypassing analysis means owning correctness. Snowflake no longer verifies that your logic produces the same result as re-running the definition. Treat it as a deliberate trade, not a default, and note it is Public Preview — confirm current status before recommending it for production. Public Preview note Custom incrementalization

The Snowflake developer guide works a full example using CHANGES(INFORMATION => APPEND_ONLY) to feed only new events while reading a dimension fresh on each refresh — a useful pattern to read before writing your own. Comprehensive Guide to Dynamic Tables

Never Ship AUTO

It hides a FULL resolution at creation and fails outright if the definition later stops being incrementalizable. Explicit modes make cost visible in the DDL.

ADAPTIVE Is the Default Answer

GA since 2026-07-30 and the documented preference for anything incrementalizable. It handles the bulk-load spike that used to force a choice between two bad modes.

Nothing Auto-Switches

There is no change-volume threshold. A misconfigured table stays expensive until a human compares refresh durations.

Check Upstream First

UPSTREAM_USES_FULL_REFRESH means the problem is a parent table, not the definition in front of you.
