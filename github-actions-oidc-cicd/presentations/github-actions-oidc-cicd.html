Secretless CI/CD: Deploying to Snowflake from GitHub Actions

OIDC replaces the stored private key with a short-lived token GitHub mints per run. The auth is the easy part — the network policy is what actually blocks you.

Recommended path is snowflakedb/snowflake-actions@v3 with use-oidc: true. Everything on the setup slides is doc-backed; the network-policy slide is marked where it draws on field experience. Snowflake CLI GitHub Action Action source

Why Secretless

A stored key pair works. It also creates three problems that never fully go away.

Rotation Is Manual

A private key in GitHub Secrets has no expiry and no rotation mechanism. It stays valid until a human remembers to replace it in both places.

Blast Radius Is Permanent

If the secret leaks, it is valid until revoked. A short-lived OIDC token issued per run is useless minutes later.

Scope Is Coarse

A key authenticates anyone holding it. An OIDC subject binds trust to a specific repository and a specific branch, PR, or environment.

Auditability Is Weaker

Key-based auth tells you a user connected. Subject-bound OIDC tells you which repository and ref the deploy came from.

The trade: you give up a secret you control and gain a trust relationship you configure once. The setup is slightly more involved; the ongoing maintenance is close to zero, because there is nothing to rotate. Workload identity federation is the underlying mechanism. Workload identity federation

How the Exchange Works

Nothing is stored. GitHub mints a token, Snowflake validates it directly.

Step 3

→
Step 4

→
Step 5
CLI runs as the service user

With use-oidc: true the action exports these for every later step in the job:

SNOWFLAKE_AUTHENTICATOR=WORKLOAD_IDENTITY
SNOWFLAKE_WORKLOAD_IDENTITY_PROVIDER=OIDC
SNOWFLAKE_AUDIENCE=snowflakecomputing.com
SNOWFLAKE_TOKEN=<short-lived GitHub OIDC token>

The action also installs Python 3.11 and uv, then installs the CLI in an isolated environment via uv tool install snowflake-cli. After it completes, snow is on PATH for the rest of the job — there is no Python version for you to manage. How it works

Three Ways to Authenticate

All three are supported. Only one avoids storing a long-lived credential.

Note What OIDC Still Needs

Even secretless, you store SNOWFLAKE_ACCOUNT as a secret. That is an identifier, not a credential — it cannot authenticate anything on its own.

When Key Pair Still Wins

Self-hosted runners on a fixed egress IP, or any provider without an OIDC trust relationship configured. Key pair remains fully supported, not deprecated.

Part 2

Setup

The Service User

One Snowflake object establishes the trust. Note TYPE = SERVICE — this user has no password and cannot log in interactively.

CREATE USER gh_deploy_ci
  TYPE = SERVICE
  WORKLOAD_IDENTITY = (
    TYPE = OIDC
    ISSUER = 'https://token.actions.githubusercontent.com'
    SUBJECT = 'repo:my-org/my-repo:ref:refs/heads/main'
  );

-- Least privilege: give the deploy role only what the pipeline touches.
CREATE ROLE deploy_ci_rl;
GRANT USAGE ON WAREHOUSE ci_wh TO ROLE deploy_ci_rl;
GRANT USAGE ON DATABASE app_db TO ROLE deploy_ci_rl;
GRANT ROLE deploy_ci_rl TO USER gh_deploy_ci;
ALTER USER gh_deploy_ci SET DEFAULT_ROLE = deploy_ci_rl;

The Issuer Is Fixed

https://token.actions.githubusercontent.com is GitHub's OIDC issuer. It is the same for every repository — only the subject varies.

One User, One Subject

A WORKLOAD_IDENTITY definition carries a single subject. Deploying from both main and pull requests means two service users, or a broader custom claim.

Because the trust is scoped to a repo and ref rather than to a secret, treat the service user as per-pipeline rather than per-team. A user bound to main in one repo cannot be replayed from anywhere else, which is most of the security benefit. WIF reference

Choosing a Subject

The SUBJECT must match the claim GitHub actually emits. Three documented formats, and one rule that overrides the others.

Subject formatMatchesWorkflow requirement
repo:<owner>/<repo>:ref:refs/heads/<branch>Push to that branchon: push, no environment: on the job
repo:<owner>/<repo>:pull_requestAny pull request eventon: pull_request, no environment: on the job
repo:<owner>/<repo>:environment:<name>Job targets a named environmentJob sets environment:, which must exist in repo settings

The rule that catches people: when a job sets environment:, GitHub emits the environment subject form regardless of the trigger. So a service user configured for ref:refs/heads/main will fail on a push if the job also declares an environment. If you add an environment for approval gating later, the subject must change too.

Need something broader — every branch in a repo, or every repo under an org — then customize the subject to include a claim such as repository_owner. That is configured on the GitHub side. GitHub OIDC reference Subject formats

The Workflow

Two things make OIDC work: the id-token: write permission and use-oidc: true. Omitting the permission is the most common first failure.

name: Deploy to Snowflake
on:
  push:
    branches:
      - main

permissions:
  id-token: write   # required: lets the job request an OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false

      - uses: snowflakedb/snowflake-actions@v3
        with:
          use-oidc: true
          cli-version: "3.16"

      - name: Deploy
        env:
          SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
        run: |
          snow connection test -x
          snow dcm deploy --target PROD -x

id-token: write

Without it GitHub will not mint a token and the action cannot authenticate. It is a job permission, not an action input.

persist-credentials: false

Stops checkout leaving a Git credential on the runner. Good hygiene in any workflow, and it costs nothing.

Pin cli-version

Omitted means latest, which means your pipeline can change under you. Pin it and bump deliberately.

-x Everywhere

Exits non-zero on error so a failed deploy fails the job instead of passing silently.

Version Pinning

Two independent things to pin: the action, and the CLI it installs.

# Floating major tag: follows the latest v3 release.
- uses: snowflakedb/snowflake-actions@v3

# Patch tag: pinned to one release.
- uses: snowflakedb/snowflake-actions@v3.0.0

# Commit SHA: fully immutable, the supply-chain-safe option.
- uses: snowflakedb/snowflake-actions@a1b2c3d4e5f67890abcdef1234567890abcdef12

Part 3

Operating It

The Network Policy Wall

Auth will be working and the deploy will still fail. This is the step nobody warns you about.

Symptom: OIDC succeeds, then Snowflake rejects the connection with 250001 — IP not allowed. GitHub-hosted runners have ephemeral IPs from very large ranges, so any account with a network policy blocks them by default. This is not an auth problem and no amount of subject-fixing will help.

-- Snowflake publishes a managed rule covering GitHub's runner ranges.
-- Attach it as a USER-level policy on the service user, so it overrides
-- the account policy for this token-only user and nothing else.
CREATE NETWORK POLICY gh_ci_policy
  ALLOWED_NETWORK_RULE_LIST = ('SNOWFLAKE.NETWORK_SECURITY.GITHUBACTIONS_GLOBAL');

ALTER USER gh_deploy_ci SET NETWORK_POLICY = gh_ci_policy;

Why User-Level

A user-level network policy overrides the account policy for that user alone. The service user can reach Snowflake from GitHub's ranges while every human account stays restricted to the corporate network.

Why the Managed Rule

Snowflake maintains the CIDR list and updates it as GitHub changes ranges. Hand-maintaining thousands of CIDRs is not a viable alternative. Network policies

Field note: where the account policy is org-managed and cannot be overridden per user, this path is closed — use a self-hosted runner on an already-allowlisted IP instead. Verify on a throwaway branch before switching a production pipeline, because a service user carries exactly one subject and a mismatch fails closed.

Named Connections

Some commands need a named connection rather than environment variables. That changes where the OIDC token has to land.

default_connection_name = "ci"

[connections.ci]
# Left empty on purpose: values arrive from the environment at run time.
- uses: snowflakedb/snowflake-actions@v3
  with:
    use-oidc: true
    default-config-file-path: "config.toml"
    # Token must be exported under the connection-specific variable name.
    oidc-token-name: SNOWFLAKE_CONNECTIONS_CI_TOKEN
- name: Deploy
  env:
    SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
  run: snow sql -c ci -q "SELECT CURRENT_USER()" -x

The Naming Rule

SNOWFLAKE_CONNECTIONS_<NAME>_TOKEN, where <NAME> is the uppercased connection name. For [connections.ci] that is SNOWFLAKE_CONNECTIONS_CI_TOKEN.

Default Is Plain

Without oidc-token-name the token exports as SNOWFLAKE_TOKEN, which only works for the default temporary connection.

Commit an Empty Block

The config.toml in the repo declares the connection name and nothing else. Values come from the environment, so no secret is committed.

Permissions Differ by OS

The copied config.toml gets 0600 on Linux and macOS. On Windows permissions are not modified — never commit secrets there regardless. Configure connections

What You Can Deploy

Once snow is on PATH and authenticated, the pipeline is ordinary CLI usage.

DCM Projects

snow dcm deploy --target PROD for declarative database change management.

dbt Projects

Deploy and execute dbt projects that run natively on Snowflake. dbt CI/CD

Streamlit

snow streamlit deploy for apps in Snowflake.

Native Apps

Application packages and versions from the same pipeline.

Plain SQL

snow sql -f migration.sql when a migration is all you need.

Design the pipeline around validate-then-deploy: run the same commands on a pull request with a PR-scoped service user against a dev target, then on merge to main with a separate main-scoped user against prod. Two subjects, two users, one workflow file. This is where the one-user-one-subject constraint stops being an annoyance and becomes the safety property.

When You Cannot Use OIDC

Key pair remains fully supported. Password is supported but should not be in a production pipeline.

- uses: snowflakedb/snowflake-actions@v3
  with:
    cli-version: "3.16.0"
- name: Deploy
  env:
    SNOWFLAKE_AUTHENTICATOR: SNOWFLAKE_JWT
    SNOWFLAKE_USER: ${{ secrets.SNOWFLAKE_USER }}
    SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
    SNOWFLAKE_PRIVATE_KEY_RAW: ${{ secrets.SNOWFLAKE_PRIVATE_KEY_RAW }}
    PRIVATE_KEY_PASSPHRASE: ${{ secrets.PRIVATE_KEY_PASSPHRASE }}
  run: |
    snow connection test -x
    snow dcm deploy --target PROD -x

Legitimate Reasons to Stay on Key Pair

An org-managed account network policy you cannot override per user. A self-hosted runner already on an allowlisted IP. A CI provider without an OIDC trust configured.

Password: Legacy Only

Supported for existing workflows, explicitly not recommended for production CI/CD. If you must, omit SNOWFLAKE_AUTHENTICATOR and pass SNOWFLAKE_PASSWORD — and enable MFA caching.

Migration from the predecessor action is a one-line change: snowflakedb/snowflake-cli-action@v2 becomes snowflakedb/snowflake-actions@v3, with identical inputs. The old path keeps working, but new workflows should use the current one. Release notes

Part 4

Limits and Alternatives

Limits and Gotchas

The things worth knowing before you commit a pipeline to this path.

GitHub Actions Only, For Now

The snow auth oidc commands are documented as currently limited to GitHub Actions as the provider. auth oidc commands

One Subject Per User

Branch, PR, and environment each need their own service user, unless you broaden the claim on the GitHub side.

The environment: Override

Adding environment: to a job silently changes the emitted subject. Adding an approval gate later will break a ref-scoped user.

No Reusable Bearer Token

OIDC yields a short-lived token for the CLI, not a static bearer you can reuse in an arbitrary HTTP header. Anything needing that still needs a PAT — scope it to those steps only.

CLI 3.11 Minimum

Older CLI versions cannot do OIDC at all. Pin at or above 3.11.

Windows Permissions

The action does not tighten config.toml permissions on Windows runners. Keep credentials in GitHub Secrets.

The action runs on Ubuntu, macOS, and Windows GitHub-hosted runners and is tested against Python 3.10 and 3.13. Validate any change on a throwaway branch first — a subject mismatch fails closed, which is safe but opaque if you are debugging under time pressure. Platform support

Beyond GitHub

Snowflake ships first-party CI/CD integrations for other providers too, at differing maturity.

GitHub Actions

snowflakedb/snowflake-actions@v3. The most complete path, and the only one with documented OIDC support today. Docs

GitLab

A Snowflake-provided CI component with a comparable shape. GitLab component

Azure DevOps

An extension covering the same deploy surface. All integrations

The Portable Part

The Snowflake side barely changes. A service user with TYPE = SERVICE, a least-privilege role, and a network policy are the same regardless of which CI system calls in.

The Provider-Specific Part

The trust configuration and the claim format differ per provider. Check current OIDC support before assuming parity with GitHub — the CLI's OIDC commands are documented as GitHub-only for now.

The Network Policy Is the Real Work

Auth is a dozen lines. The 250001 IP rejection is what actually stops the first attempt, and it is fixed with a user-level policy using the managed GitHub Actions rule.

One Subject Per User

Treat service users as per-pipeline, not per-team. PR-scoped and main-scoped users give you validate-then-deploy for free.

Watch for environment:

It overrides the subject form regardless of trigger. Adding an approval gate later means updating the service user too.

Pin Both Versions

Pin the action to a SHA and the CLI with cli-version. Unpinned means your pipeline changes without a commit.
