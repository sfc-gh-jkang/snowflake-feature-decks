Interactive Tables, Fed Directly by Snowpipe Streaming

One table is both the streaming target and the sub-second serving layer — no landing table, no COPY INTO, no rollup hop.

Read this first: both halves are GA — interactive tables GA Dec 2025, Snowpipe Streaming HPA GA Sep 2025 — and the direct-streaming pattern is documented in an official Snowflake quickstart: Real-Time Streaming with Snowpipe Streaming and Interactive Tables. What it is not is described in the interactive-tables product guide, which never mentions streaming, channels, or pipes and presents TARGET_LAG auto-refresh as the way to populate the table. That split is why the pattern is easy to miss — see Support Status.

The Problem

Streaming freshness and sub-second serving pull in opposite directions once you add a hop between them.

Every Hop Adds Lag

Stream into a landing table, then refresh a rollup on a schedule. End-to-end freshness is now ingest latency plus refresh lag — and the refresh lag usually dominates.

TARGET_LAG Has a Floor

Auto-refresh is the documented path for interactive tables, but the minimum TARGET_LAG is 60 seconds. For a live trading or ops dashboard, a one-minute floor is the whole problem.

Interactive Warehouses Are Walled

An interactive warehouse cannot query standard tables at all. Any join has to be between interactive tables on the same warehouse, so a normalized model forces you back to a standard warehouse.

Two Objects, Two Truths

A separate rollup means the serving object and the system of record can silently diverge — and the README will describe whichever one you meant, not the one being read.

The pattern below collapses the hops: the streaming channel writes into the interactive table itself, so serving freshness equals ingest latency. The cost is that you take on the constraints of a table that rejects almost all DML.

Why It Works

Snowpipe Streaming HPA routes all ingestion through a PIPE object, and the pipe targets a table. Nothing in the HPA contract requires that table to be a standard one. Opening a channel against an interactive table causes Snowflake to auto-create the default pipe for it, exactly as it would for any other table.

What You Give Up

Interactive tables reject ordinary DML, so you cannot seed or correct rows with INSERT or DELETE. Every write — including the initial baseline — has to travel the streaming path. Plan corrections as re-streamed snapshots.

The design consequence: because an interactive warehouse can only join interactive tables, denormalize dimension attributes onto the streamed events. Serving queries then never need a join, and the aggregation happens at query time against a single clustered table.

Creating the Table

Two gotchas that cost the most time: the required clustering key, and the fact that you cannot convert an existing table.

-- You cannot CREATE OR REPLACE across table types. Converting a standard table
-- to an interactive one fails with "Object already exists as TABLE", so drop
-- the auto-created streaming pipe and the table first.
DROP PIPE IF EXISTS analytics.live."RAW_EVENTS-STREAMING";
DROP TABLE IF EXISTS analytics.live.RAW_EVENTS;

-- CLUSTER BY is REQUIRED. Choose the column your most time-critical WHERE
-- clause filters on, so serving queries prune micro-partitions.
CREATE INTERACTIVE TABLE analytics.live.RAW_EVENTS (
    EVENT_ID        VARCHAR       NOT NULL,
    EVENT_TS        TIMESTAMP_NTZ NOT NULL,
    POSITION_ID     VARCHAR       NOT NULL,
    SECTOR          VARCHAR,                 -- denormalized: no join at serve time
    RATING          VARCHAR,
    CURRENT_MARK    NUMBER(18,4),
    PAYLOAD         VARIANT,
    IS_WATCHLIST    BOOLEAN       DEFAULT FALSE
)
CLUSTER BY (EVENT_TS);

CLUSTER BY Is Mandatory

Unlike a standard table, CREATE INTERACTIVE TABLE will not compile without it. It drives the pruning that makes sub-second serving possible, so match it to your hottest filter. Clustering keys

Column Lists Work

The docs describe CTAS, but an explicit column list — with NOT NULL, DEFAULT, VARIANT, and BOOLEAN — is accepted and verified. That matters here, because there is no source table to select from. CREATE INTERACTIVE TABLE

Create From a Standard Warehouse

Run the DDL on a standard warehouse. The interactive warehouse is only for querying — it cannot run this statement.

No TARGET_LAG here, deliberately. Adding it would make this an auto-refreshing table sourced from another table, which reintroduces the refresh hop this pattern exists to remove. Leaving it off is what makes the streaming channel the sole writer.

The Streaming Producer

Ordinary HPA SDK code. Nothing here is interactive-table specific — that is the whole point.

class StreamingService:
    """HPA producer: a channel pool with partition-based routing so rows for
    one entity always land in order."""

    def __init__(self, database, schema, table, partition_count=4):
        self.table = table
        # The auto-created default pipe follows <TABLE>-STREAMING. Opening a
        # channel against it is what causes Snowflake to create the pipe.
        self.pipe_name = f"{table}-STREAMING"
        self.partition_count = partition_count

    def open_channels(self):
        self.client = StreamingIngestClient(
            db_name=self.database,
            schema_name=self.schema,
            pipe_name=self.pipe_name,
        )
        self.channels = []
        for i in range(self.partition_count):
            ch, _ = self.client.open_channel(f"{self.table}_p{i}")
            self.channels.append(ch)

    def append(self, row, partition):
        # wait_for_flush blocks until HPA commits, which is what lets you
        # measure true end-to-end ingest-to-query latency.
        self.channels[partition].append_row(row)
        self.channels[partition].wait_for_flush(timeout_seconds=10)

The Pipe Name Is the Contract

<TABLE>-STREAMING is the default pipe Snowflake creates when a channel is opened against a table. Point the SDK at it and the interactive table receives rows like any other target. HPA SDK tutorial

Seeding Travels the Same Path

Because DML is rejected, the initial baseline cannot be inserted with SQL. Have the producer emit one baseline row per entity at startup. Corrections are re-streamed snapshots, not updates.

Partition by entity key when per-entity ordering matters. Each channel preserves order within itself but not across channels, so routing one entity to one channel is what keeps its event sequence intact. Soft limits are 2,000 channels per pipe and 12 MBps per channel. HPA limits

Warehouse Pairing

The table and the warehouse are explicitly bound. This step is easy to forget and the symptom is "it works but it is slow".

-- The interactive warehouse. Minimum size is XSMALL; a fallback warehouse
-- catches anything that runs long so it cannot occupy the low-latency pool.
CREATE WAREHOUSE IF NOT EXISTS live_serving_wh
  WAREHOUSE_TYPE = 'INTERACTIVE'
  WAREHOUSE_SIZE = 'XSMALL'
  COMMENT = 'Sub-second serving for the live dashboard';

-- Associate each interactive table with the warehouse that serves it.
-- Without this the warehouse will not warm the table.
ALTER WAREHOUSE live_serving_wh ADD TABLES (analytics.live.RAW_EVENTS);

-- Serving query: aggregate at query time, filter on the clustering key.
SELECT POSITION_ID, SECTOR, CURRENT_MARK
FROM analytics.live.RAW_EVENTS
WHERE EVENT_TS >= DATEADD(hour, -24, SYSDATE())
QUALIFY ROW_NUMBER() OVER (PARTITION BY POSITION_ID ORDER BY EVENT_TS DESC) = 1;

The Wall Is One-Way

An interactive warehouse can only read interactive tables. A standard warehouse can read them too — which is what makes an A/B latency comparison possible on the same object. CREATE INTERACTIVE WAREHOUSE

Warming Is Capped at 10

Proactive warming currently covers 10 interactive tables. You can query more than that, but only ten get pre-warmed. Support can raise it.

Configure a Fallback

Queries running past 5 seconds are transparently re-run on the fallback warehouse, freeing the interactive pool. Without one configured you lose that isolation.

Cost Traps

Interactive warehouses do not bill like standard ones. This is the single most surprising part of the feature.

What That Means in Practice

A standard warehouse idles down in 60 seconds. An interactive warehouse holds for a minimum of 24 hours because its speed comes from a warm data cache that is expensive to rebuild.

Treat it as an always-on serving tier with a daily floor, not a burst resource. If the workload is not continuous, this is the wrong feature.

Resuming is not free either. Expect significant query latency right after a resume while the cache re-warms — so "suspend it overnight to save money" both costs an hour of billing and gives your first users the worst latency of the day. Auto-suspend and auto-resume

Limits

Everything below is documented. Read it before designing, because several of these are load-bearing.

DML Is Almost Entirely Out

UPDATE and DELETE are unsupported. The only permitted DML is INSERT OVERWRITE. The documented alternative is auto-refresh with DML applied to the source table.

No Streams

You cannot create a stream on an interactive table, so CDC-style downstream consumption has to come from somewhere else in the pipeline.

Not a Dynamic Table Base

A dynamic table cannot use an interactive table as a base table. Chain in the other direction: interactive tables can be built from other sources.

ALTER TABLE Is Restricted

No ADD COLUMN or REMOVE COLUMN. You can rename, set comments, and attach masking, row-access, join, aggregation, and storage-lifecycle policies.

No Fail-Safe

Fail-safe recovery does not apply. Time Travel does work, inheriting DATA_RETENTION_TIME_IN_DAYS from the schema — you cannot set it on the table.

No Stored Procedures

An interactive warehouse cannot run CALL, and cannot use the ->> pipe operator, which relies on procedures internally.

Materialized views on interactive tables require the INTERACTIVE keyword; a standard materialized view cannot use one as its source. Query Insights are not collected for queries executing on interactive tables. Full limitations list

Verifying Your Own Claims

Provisioning an interactive table proves nothing about whether anything reads it. Check all three gates.

-- Gate 1: is the object actually the type you claim?
SHOW INTERACTIVE TABLES IN SCHEMA analytics.live;
-- target_lag NULL + refresh_warehouse NULL means nothing auto-refreshes it,
-- so any rows present arrived some other way.

-- Gate 2: does a streaming pipe really target it?
SHOW PIPES IN SCHEMA analytics.live;
-- Look for kind = STREAMING and is_snowflake_managed = true.

-- Gate 3: is it exercised, on the warehouse you claim?
SELECT WAREHOUSE_NAME, COUNT(*) AS queries,
       MEDIAN(TOTAL_ELAPSED_TIME) AS p50_ms
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE QUERY_TEXT ILIKE '%RAW_EVENTS%'
  AND QUERY_TYPE = 'SELECT'
  AND START_TIME >= DATEADD(day, -7, CURRENT_TIMESTAMP())
GROUP BY 1 ORDER BY queries DESC;

-- Negative control: prove no SQL wrote the rows.
SELECT QUERY_TYPE, COUNT(*)
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE QUERY_TEXT ILIKE '%RAW_EVENTS%' AND QUERY_TYPE <> 'SELECT'
  AND START_TIME >= DATEADD(day, -40, CURRENT_TIMESTAMP())
GROUP BY 1;

Then stop the claim from silently regressing. Naming an object after a feature is not the same as using it:

// CI guard: assert the serving layer reads the object the docs brag about.
// This exists because a shadow view is invisible in a README review.
describe("queries.ts - interactive source", () => {
  it("no query references the retired rollup table or view", () => {
    for (const [name, sql] of ALL_QUERIES) {
      expect(`${name}:${sql}`).not.toMatch(/PORTFOLIO_LIVE/);
    }
  });

  it("every query reads from an interactive table", () => {
    for (const [name, sql] of ALL_QUERIES) {
      const readsIT = sql.includes(`${SCHEMA}.RAW_EVENTS`)
                   || sql.includes(`${SCHEMA}.POSITION_BOOK`);
      expect(`${name}:${readsIT}`).toBe(`${name}:true`);
    }
  });

  it("no query joins the dimension table", () => {
    for (const [name, sql] of ALL_QUERIES) {
      expect(`${name}:${sql}`).not.toMatch(/POSITIONS_DIM/);
    }
  });
});

The failure this prevents: a demo shipped with an interactive table provisioned, an interactive warehouse running, and a README describing both — while every dashboard query read a plain view over a standard table. The DDL was added to tell the story; the query layer was copied from the parent fork and never repointed. The claim lived in Markdown, reality lived in code, and nothing diffed them.

One Object, One Truth

The streaming target and the serving layer are the same table, so freshness equals ingest latency and there is no second object to diverge.

Denormalize Deliberately

Interactive warehouses only join interactive tables. Push dimension attributes onto the events so serving queries never join.

Append-Only Thinking

DML is effectively unavailable. Design corrections as re-streamed snapshots and take latest-per-key at query time.

Always-On Economics

A 24-hour minimum auto-suspend makes this a serving tier, not a burst resource. Continuous workloads only.
