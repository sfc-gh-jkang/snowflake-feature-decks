EXTERNAL + Free: What a Private App Listing Actually Requires

A private listing of a Native App has no Snowflake approval gate. It has an automated security scan, and the scan is triggered by your DISTRIBUTION setting — not by the listing.

What EXTERNAL + Free Means

Two independent settings that get conflated. One controls who can install; the other controls who pays.

DISTRIBUTION = INTERNAL

You can only create a private listing within the same organization where the application package was created. The automated security scan is not performed.

DISTRIBUTION = EXTERNAL

You can create listings outside your organization: private listings to other orgs, public listings, and Marketplace listings. This is what turns the scan on.

Free

A pricing choice, not a distribution choice. No provider profile and no Stripe account required. Free and EXTERNAL are orthogonal.

The one sentence to remember: DISTRIBUTION decides whether Snowflake scans your code. The listing type decides whether Snowflake reviews your listing. A private listing skips the second entirely but not the first.

Provider profile requiredNo, not for private listings

What Snowflake Does Not Review

This is the single most expensive misread in the private-listing docs, and it costs teams weeks of imaginary lead time.

The trap: the “Submit for Approval” step on the create-and-publish page is Marketplace-only. The page documents two separate publish paths under one heading. Teams read the Marketplace path, assume it applies to them, and build a release plan around a Snowflake response date that does not exist.

StepPrivate listingMarketplace listing
Provider profileNot requiredRequired
Submit for approvalNo such stepRequired, every listing
Functional review by Marketplace OpsNoYes
Enforced app standards verifiedNoYes, at submission
Automated security scanYes, if EXTERNALYes

The enforced standards page

The app quality standards — immediate utility, standalone, data-centric, transparent — are verified when you submit a listing to Snowflake Marketplace. They are not a gate on a private listing. Treat them as a design target if you might go public later, not a requirement today.

Shared responsibility still applies

The provider is the seller of record, not Snowflake. Snowflake’s scanning is explicitly not a substitute for your consumer’s own due diligence. Expect their security team to ask for the privilege list regardless.

What Snowflake Does Scan

The scan is real, automated, and entirely self-service. You start it, you watch it, and it does not wait on a human at Snowflake unless it fails.

Step 4

-- Release channels are enabled by default on new packages,
-- so ADD VERSION is rejected -- use REGISTER VERSION
ALTER APPLICATION PACKAGE analytics_prod_pkg
  REGISTER VERSION v1
  USING '@app_build_db.src.app_src';

-- Adding to ALPHA or DEFAULT starts the security scan.
-- Adding only to QA does not.
ALTER APPLICATION PACKAGE analytics_prod_pkg
  MODIFY RELEASE CHANNEL DEFAULT ADD VERSION v1;

Release channels are enabled by default on new application packages. ALTER APPLICATION PACKAGE ... ADD VERSION is rejected with “Release channels enabled ... Use REGISTER/DEREGISTER instead of ADD/DROP version syntax”. Many older examples still show ADD VERSION.

The three default channels state the scan contract in their own descriptions:

DEFAULTAll versions passed Snowflake security and functional review
ALPHAMay contain versions where security review was not approved before release
QAMay contain versions never reviewed by Snowflake. Internal testing only
SHOW VERSIONS IN APPLICATION PACKAGE analytics_prod_pkg;

-- review_status: NOT_REVIEWED -> IN_PROGRESS -> APPROVED | REJECTED
SELECT "version", "patch", "review_status", "release_channel_names"
FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()));

Turnaround: registered at 13:22, APPROVED by roughly 13:26 — about four minutes. That is a floor, not a promise: a trivial app with no dependencies gives the CVE scanner nothing to do. Budget more for a real app, but the point stands that this is minutes-to-hours self-service, not a multi-week review queue.

When the scan fails

REJECTED triggers a manual Snowflake review, and the rejection reason is readable on the application package. Only at this point is a human at Snowflake in your path.

Appeals

Open a severity 4 support ticket. A CVE-based appeal needs why the CVE is not exploitable, a reachability analysis if available, and a plan for updating — or a detailed reason you cannot.

Every version, every patch

A package already set to EXTERNAL scans each new version or patch immediately. Flipping DISTRIBUTION on an existing package scans the 10 most recent patches of every version. Build the scan into your release cadence.

The ongoing-monitoring and 30-business-day remediation window described in the scan documentation is written as applying to apps “approved and published on the Snowflake Marketplace.” Whether that same window attaches to a private-listing-only app is not stated on that page. Per-version and per-patch rescanning is documented and certain; the monitoring SLA is Marketplace-scoped language and is flagged here rather than asserted either way.

The Scan Checklist

Code against this before you flip DISTRIBUTION, not after the scan rejects you.

Code

No code loaded or executed from outside the application package except Snowflake-provided libraries. All code human-readable — minified JavaScript needs a source map. No dependencies carrying critical or high CVEs.

Secrets and transport

No plain-text customer secrets, stored or required. All Internet communication over HTTPS with a valid TLS certificate.

Disclosure in the listing

All functionality and features. Every Internet endpoint and URL the app connects to. Every external function. Any consumer data logged, collected, or stored. Non-essential cookies prohibited; essential ones disclosed.

Privileges

The manifest declares every privilege on every object and all API integrations. Request the minimum set that makes the app work — and expect the consumer to read the list.

No harm

No data leakage or loss, no restricting consumer access to their own data unless that is the point of the app, no excessive resource consumption, no arbitrary code injection or execution.

Behaves as advertised

The app should do what the listing says, and installation and setup instructions belong in the listing.

The documented best practice that most directly protects a release date: run two application packages. A development package on INTERNAL so iteration never triggers a scan, and a production package on EXTERNAL that only receives versions you have already reviewed.

-- Development package: iterate freely, never scanned
CREATE APPLICATION PACKAGE analytics_dev_pkg
  DISTRIBUTION = INTERNAL;

-- Production package: this is the one Snowflake scans
CREATE APPLICATION PACKAGE analytics_prod_pkg
  DISTRIBUTION = EXTERNAL;

App specifications require manifest_version: 2, which also enables automated granting of privileges:

manifest_version: 2
version:
  name: v1
artifacts:
  readme: readme.md
  setup_script: setup.sql
privileges:
  - CREATE EXTERNAL ACCESS INTEGRATION:
      description: "Allows the app to create an EAI."

Indentation trap, verified by execution: the privileges example as indented in the docs puts description at the same level as the privilege name. YAML parses that as one map with two keys, and Snowflake rejects it:

Error parsing 'manifest.yml' ... Manifest field 'privileges' may only specify a single attribute per item.

description must be nested one level deeper, under the privilege key. This is what the rejected form looks like:

privileges:
  - CREATE EXTERNAL ACCESS INTEGRATION:
    description: "Allows the app to create an EAI."

Setting manifest_version: 2 means consumers agree at install time that the app may be granted the declared privileges during upgrades without additional consent. Consumers can constrain this with feature policies that limit which objects an app may create.

The Auth Requirement

The requirement most likely to force an architecture change rather than a checklist fix. If your app has a UI, read this first.

Snowflake authentication must come first. All connections to an app — including web-based user interfaces and APIs — must first authenticate using a Snowflake-provided method. Any app-specific authentication must be presented to users only after Snowflake authentication has succeeded. Apps must not create public endpoints reachable without successful Snowflake authentication.

Why this breaks designs

A team porting an existing SaaS product often assumes their own login page fronts the app. Inside a Native App it cannot. Your login screen can exist, but only behind Snowflake auth — never in front of it.

What is allowed

Asking a consumer to create a service user in their account purely to reach an external service is acceptable, using a Programmatic Access Token, OAuth, or key pair, granted minimum permissions.

What is never allowed

Requiring the consumer to type their Snowflake username and password into your app, or to generate a keypair and hand you the private key.

Check this before you write the scan checklist off as paperwork. Every other item on the previous slide is a fix. This one can be a redesign, and it is cheapest to discover now.

Source: Security requirements and best practices for a Snowflake Native App

External Access and OAuth

Outbound calls are requested through app specifications, approved per-consumer, and can be partially granted. The app has to cope with that.

Step 1
Declare privilege in manifest
→
Step 2
Setup script creates rule, EAI, spec
→
Step 3
Consumer approves host ports
→
Step 4
App verifies, then calls
-- In the setup script. Runs in the CONSUMER account at install time.
CREATE OR REPLACE NETWORK RULE setup.partner_api_rule
  TYPE = HOST_PORT
  VALUE_LIST = ('api.example.com')
  MODE = EGRESS;

CREATE OR REPLACE EXTERNAL ACCESS INTEGRATION partner_api_eai
  ALLOWED_NETWORK_RULES = (setup.partner_api_rule)
  ENABLED = TRUE;

-- HOST_PORTS must match the network rule VALUE_LIST.
-- The EAI exists but is NOT usable until the consumer approves this.
ALTER APPLICATION SET SPECIFICATION partner_api_spec
  TYPE = EXTERNAL_ACCESS
  LABEL = 'Connection to the partner API'
  DESCRIPTION = 'Reads reference metadata from an API outside Snowflake'
  HOST_PORTS = ('api.example.com');

Partial approval is the case to design for. An app may request access to several endpoints and the consumer might allow only one. The EAI is created in the consumer account but is not usable until the specification is approved, and the app must confirm approval before making API calls. An app that assumes all-or-nothing will fail in production at a customer who approved three of four hosts.

Ports must match

Endpoints and ports in the app specification must match the values in the network rule’s VALUE_LIST. A mismatch is a silent misconfiguration until a call fails.

One spec covers all EAIs

A single app specification applies to every EAI the app creates. Multiple specifications are supported but not required — split them when you want independently approvable groups of endpoints.

Disclose the endpoints

Every Internet endpoint and URL the app connects to must be disclosed in the listing. The specification list and the listing disclosure need to agree.

Release Directives

A listing cannot be published until a release directive exists. It is also the mechanism for piloting a version with a subset of customers.

-- Required before a listing can be published.
ALTER APPLICATION PACKAGE analytics_prod_pkg
  MODIFY RELEASE CHANNEL DEFAULT
  SET DEFAULT RELEASE DIRECTIVE VERSION = v1 PATCH = 0;

-- Pilot a version with named accounts. ACCOUNTS comes BEFORE VERSION.
ALTER APPLICATION PACKAGE analytics_prod_pkg
  SET RELEASE DIRECTIVE pilot_customers
  ACCOUNTS = (myorg.pilot_acct)
  VERSION = v1 PATCH = 0;

Argument order is not interchangeable. For SET RELEASE DIRECTIVE, ACCOUNTS comes before VERSION and PATCH. Putting VERSION first fails with syntax error ... unexpected 'VERSION'. Some channel-oriented examples show the reverse order; the reference syntax page is authoritative.

Default vs custom

The default release directive sets what every consumer installs. A custom directive overrides it for named accounts, and a custom directive always takes precedence.

Piloting safely

Point a custom directive at two friendly accounts, leave the default on the previous version, and promote only after they confirm. Use FORCE to atomically move accounts already assigned elsewhere.

Respecting maintenance windows

UPGRADE_IN_MAINTENANCE_WINDOW = TRUE defers upgrades to the consumer’s window, and requires UPGRADE_DEADLINE. It cannot be combined with UPGRADE_AFTER.

Sources: ALTER APPLICATION PACKAGE ... RELEASE DIRECTIVE · Release channels

Cross-Region and Cost

Where a free listing stops being free — for you, not your consumer.

“Free” means free to the consumer. If any consumer sits in a different region or cloud than the account hosting your application package, Cross-Cloud Auto-Fulfillment replicates it — and the provider incurs the compute, storage, and egress cost of that replication. More consumer regions means higher cost, driven mostly by data transfer.

Fulfillment is demand-driven

Private listings are auto-fulfilled after the specified consumers get the listing. You are not paying to pre-stage every region, only the ones with active consumers.

Costs land on a secure share area

Snowflake creates one secure share area per region for the organization and attributes the cost there, so it will not show up under your normal warehouse attribution. Track it with LISTING_AUTO_FULFILLMENT_USAGE_HISTORY in ORGANIZATION_USAGE.

Egress Cost Optimization

ECO can materially reduce the transfer component. Worth enabling before you scale to many consumer regions rather than after the first bill.

-- Without this, remote-region consumers stay pinned to an old version.
ALTER APPLICATION PACKAGE analytics_prod_pkg
  SET LISTING_AUTO_REFRESH = TRUE;

-- On-demand push. Takes TWO arguments: type, then name.
SELECT SYSTEM$TRIGGER_LISTING_REFRESH('LISTING', 'MY_LISTING_GLOBAL_NAME');

The silent version-drift bug: an application package attached to a listing does not automatically propagate new versions to remote regions. Without LISTING_AUTO_REFRESH, or an explicit SYSTEM$TRIGGER_LISTING_REFRESH, consumers in other regions stay on an older version while your home region looks correct. Track refreshes with LISTING_REFRESH_HISTORY.

One-way door: after you publish a private listing, you cannot change the share associated with it. Decide the data product before you publish, not after.

Net: for an EXTERNAL free private listing there is no Snowflake approval to wait on. The work is a self-service security scan you can start today, an auth model you should validate before writing more code, and a cross-region cost decision that belongs to you rather than your consumer.
