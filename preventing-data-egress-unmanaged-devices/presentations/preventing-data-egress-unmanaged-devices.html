Preventing Data Download to Unmanaged Devices

You cannot turn off the download button. You can make sure the person holding the phone never gets a session in the first place — and that is a stronger control anyway.

Every SQL statement in this deck was executed against a live Snowflake account (Enterprise Edition, AWS us‑east‑1) on 2026-08-03. Object-creation and policy-behaviour statements were run and their effects verified; the two account-wide activation statements (ALTER ACCOUNT SET NETWORK_POLICY and SET AUTHENTICATION POLICY … FOR ALL PERSON USERS) were compile-validated only, because executing them with the example values in this deck would lock you out of your own account. Treat those two lines as the last step of a planned change, not something to paste into a worksheet.

The Real Question

Security teams usually arrive with a specific ask: stop people downloading company data onto a phone. That is a reasonable goal, but it is phrased as a UI problem, and the UI is the one place Snowflake gives you no switch.

Reframing it as an access problem makes it solvable, because a download requires four things to line up first:

1
A reachable endpoint
→
2
A successful authentication
→
3
A live session
→
4
Readable data in the result

Take away: break any one of the first three and step four never happens. Every control in this deck attacks steps 1–3. Attacking step 4 alone — the download button — is the only approach that does not work.

Why "Block the UI" Is the Wrong First Move

The instinct is to restrict the web UI with an authentication policy. It is worth doing, but if it is your only control you have bought less than you think. Snowflake says so explicitly, three separate times on one page.

Verbatim from the Snowflake docs: "The CLIENT_TYPES property of an authentication policy is a best-effort method to block user logins based on specific clients. It should not be used as the sole control to establish a security boundary. Notably, it does not restrict access to the Snowflake REST APIs."

A phone with a valid credential can call the SQL REST API and receive JSON. No browser involved, so no browser control applies. That is why identity and network come first.

Layer 1 — Identity: Where Device Posture Actually Lives

Snowflake does not evaluate whether a device is corporate-managed, encrypted, jailbroken, or MDM-enrolled. It has no concept of device posture. Your identity provider does, and Snowflake honours the outcome by trusting the federated assertion.

Snowflake's job

Accept or reject an authentication method. Restrict which IdP a user may use. Enforce MFA. Nothing device-aware.

The IdP's job

Decide whether this device is allowed to complete the login at all — compliant, managed, hybrid-joined, or blocked.

Why this ordering wins

A personal phone fails the check before a Snowflake session exists. There is no result set to download.

With Microsoft Entra ID, the relevant grant control is Require device to be marked as compliant, which supports iOS, Android, Windows, macOS and Linux devices registered with Entra ID and enrolled in Intune. Okta, Ping and others expose an equivalent device-trust condition.

The gap that quietly undoes all of it: any user who still holds a local Snowflake password can bypass the IdP entirely, and with it every Conditional Access rule you wrote. Federating the IdP is only half the job — you must also remove password as an allowed authentication method for human users.

-- Force every human through the IdP so Conditional Access can evaluate device posture
CREATE AUTHENTICATION POLICY mydb.security.sso_only_humans
  AUTHENTICATION_METHODS = ('SAML')
  CLIENT_TYPES = ('SNOWFLAKE_UI', 'DRIVERS')
  MFA_ENROLLMENT = 'OPTIONAL'
  COMMENT = 'Humans authenticate via IdP only; device posture enforced upstream';

ALTER ACCOUNT SET AUTHENTICATION POLICY mydb.security.sso_only_humans
  FOR ALL PERSON USERS;

-- Keep a non-restrictive policy on a break-glass admin to avoid lockout
ALTER USER breakglass_admin
  SET AUTHENTICATION POLICY mydb.security.admin_fallback_policy;

Verified hard error — and it bites the "just block the UI" instinct directly: if you set MFA_ENROLLMENT = 'REQUIRED' and leave SNOWFLAKE_UI out of CLIENT_TYPES, the statement is rejected: "If MFA_ENROLLMENT = 'REQUIRED', CLIENT_TYPES must include SNOWFLAKE_UI to allow for enrollment." Excluding the web UI therefore forces MFA_ENROLLMENT = 'OPTIONAL', which weakens Snowflake-native MFA enrollment. When the IdP owns MFA this is the correct trade, but make it deliberately rather than discovering it in an error message.

Policy precedence runs network → authentication → password → session. A network policy match short-circuits evaluation before the authentication policy is even read, which is why Layer 2 is the cheapest broad control you own.

Layer 2 — Network: The Control Most Accounts Have Built but Not Turned On

Straight from the docs: "By default, Snowflake allows users to connect to the service and internal stage from any computer or device." A network policy narrows that to your corporate egress — VPN, SASE or proxy ranges — which alone removes the coffee-shop and cellular-data scenarios.

-- Network rules live in a schema; the network policy itself is account-level
CREATE NETWORK RULE mydb.security.corp_egress_rule
  MODE = INGRESS
  TYPE = IPV4
  VALUE_LIST = ('203.0.113.0/24', '198.51.100.0/24');

CREATE NETWORK POLICY corp_only_policy
  ALLOWED_NETWORK_RULE_LIST = ('mydb.security.corp_egress_rule');

-- A policy does NOTHING until it is activated. This line is the actual control.
ALTER ACCOUNT SET NETWORK_POLICY = corp_only_policy;

-- Verify. A blank value means no policy is active.
SHOW PARAMETERS LIKE 'NETWORK_POLICY' IN ACCOUNT;

The single most common failure: "A network policy doesn't restrict network traffic until it is activated." Creating the policy object changes nothing. Teams routinely build a policy, see it in SHOW NETWORK POLICIES, and believe they are covered. Confirm activation with SHOW PARAMETERS LIKE 'NETWORK_POLICY' IN ACCOUNT — if the value is blank, the policy is inert.

Use network rules, not IP lists

New policies should use ALLOWED_NETWORK_RULE_LIST. ALLOWED_IP_LIST still works but Snowflake advises against mixing both in one policy.

Enumerate the full egress range

SASE and proxy vendors publish many egress IPs per data centre. A policy containing one address will strand users the moment traffic shifts nodes.

Activate at three scopes

Account, user, and security integration. Service accounts usually want a tighter, separate policy from humans.

If you need the strongest version of this control, privatelink-only enforcement disables public access to your account endpoints entirely — an unknown caller gets HTTP 404 account not found. It requires Business Critical Edition or higher, and any SaaS tool that cannot use private connectivity will stop working, so inventory integrations first.

Layer 3 — Session: Shorten the Window

Even with everything above correct, a session already established on a device stays usable for a long time by default. The web UI and the drivers have separate timeouts, and the web UI default surprises most people.

SESSION_UI_IDLE_TIMEOUT_MINS (Snowsight)Default 1080 min — 18 hours
SESSION_IDLE_TIMEOUT_MINS (clients, programmatic)Default 240 min — 4 hours
Permitted range, both5 to 1440 minutes
Also availableSESSION_MAX_LIFESPAN_MINS, SESSION_UI_MAX_LIFESPAN_MINS

An 18-hour idle window means a browser tab opened once in the morning is still live that evening, wherever the device has travelled. Max-lifespan caps force a genuine re-authentication regardless of activity, which re-runs your IdP device check.

-- Snowsight default idle timeout is 1080 minutes (18 hours)
CREATE SESSION POLICY short_idle_policy
  SESSION_UI_IDLE_TIMEOUT_MINS = 30
  SESSION_IDLE_TIMEOUT_MINS = 60
  SESSION_UI_MAX_LIFESPAN_MINS = 480;

ALTER ACCOUNT SET SESSION POLICY short_idle_policy;

Layer 4 — Limit What Is Downloadable at All

If a session is legitimate, the remaining question is what lands in the result set. Snowflake's five data protection policy types shape query output at run time, independently of role grants. All require Enterprise Edition or higher.

Masking policy

Column-level. Returns a masked value at query time, so the export contains the mask, not the secret.

Row access policy

Row-level. Restricts which rows are visible for SELECT, UPDATE, DELETE and MERGE.

Projection policy

The most underused one here: a column can be filtered on but cannot be projected into output. Directly blocks "SELECT it and export it".

Aggregation policy

Forces minimum group sizes, so no individual row can be isolated out of a small group.

Join policy

Controls how datasets may be combined, limiting re-identification by correlation.

Apply via tags

Attach policies to a governance tag rather than each column, so new sensitive columns inherit protection automatically.

-- Projection policy: column is queryable for filters but cannot be SELECTed out
CREATE PROJECTION POLICY no_export_ssn
  AS () RETURNS PROJECTION_CONSTRAINT ->
  CASE
    WHEN CURRENT_ROLE() = 'FRAUD_ANALYST' THEN PROJECTION_CONSTRAINT(ALLOW => TRUE)
    ELSE PROJECTION_CONSTRAINT(ALLOW => FALSE)
  END;

ALTER TABLE customers MODIFY COLUMN ssn
  SET PROJECTION POLICY no_export_ssn;

Operational caveat, verified: a projection policy does not silently omit the column. Both SELECT ssn and bare SELECT * fail outright with "The following columns are restricted by a Projection Policy." Any existing query, view or BI extract using SELECT * against the table will break the moment you apply the policy. Inventory SELECT * usage first, and expect to pin explicit column lists.

Why this layer matters for the mobile question: it is the only layer that still helps when access is entirely legitimate. A managed laptop on the corporate network downloading a masked column is a non-event.

Layer 5 — Close the Bulk Export Paths

The browser download button moves a result grid. COPY INTO <location> moves a table. It can unload to an internal stage, which is then pulled to local disk with GET, or to an external bucket. These parameters govern that path and are all off by default.

-- Block COPY INTO -> internal stage -> GET, and inline presigned-URL unloads
ALTER ACCOUNT SET PREVENT_UNLOAD_TO_INTERNAL_STAGES = TRUE;
ALTER USER analyst_user SET PREVENT_UNLOAD_TO_INLINE_URL = TRUE;

-- Force unloads through governed storage integrations only
ALTER ACCOUNT SET REQUIRE_STORAGE_INTEGRATION_FOR_STAGE_CREATION = TRUE;
ALTER ACCOUNT SET REQUIRE_STORAGE_INTEGRATION_FOR_STAGE_OPERATION = TRUE;

-- Apply network rules to internal stage traffic too
ALTER ACCOUNT SET ENFORCE_NETWORK_RULES_FOR_INTERNAL_STAGES = TRUE;
ParameterScopeWhat it closes
PREVENT_UNLOAD_TO_INTERNAL_STAGESAccount and user (user wins)Unload to internal stage, then GET to local disk
PREVENT_UNLOAD_TO_INLINE_URLUserUnload addressed at an inline URL
REQUIRE_STORAGE_INTEGRATION_FOR_STAGE_CREATIONAccountAd-hoc stages pointing at unapproved buckets
REQUIRE_STORAGE_INTEGRATION_FOR_STAGE_OPERATIONAccountOperating a stage with inline credentials
ENFORCE_NETWORK_RULES_FOR_INTERNAL_STAGESAccountStage traffic that ignores your network policy

Both PREVENT_UNLOAD parameters are ACCOUNTADMIN-only to set, and as of the 2025_01 behaviour change PREVENT_UNLOAD_TO_INTERNAL_STAGES is settable at account and user level, with the user-level value taking precedence. Audit for user-level overrides before declaring the account covered.

Also inventory the OAuth and connector integrations that read your data — BI tools, automation platforms, and AI assistants. Each is an egress path reachable from a phone that no browser or driver control touches, because the data leaves through the integration rather than the user's device. Enumerate them, scope each to the narrowest role, and use CLIENT_TYPES = ('DRIVERS') on their service users so they cannot be replayed to sign in to the web UI.

Layer 6 — Prove It, Then Watch It

Preventive controls need evidence that they are on and staying on. Two built-in surfaces cover most of it, with no pipeline to build.

Trust Center

Evaluates the account against scanner recommendations and raises findings. Includes secure-authentication readiness and whether MFA is enforced for all human users — the fastest way to find the accounts still holding a local password.

ACCESS_HISTORY

Which query touched which table and column, and who ran it. The column-level detail is what lets you answer "was regulated data actually read", not just "was a query run".

AGGREGATE_ACCESS_HISTORY

The same access picture aggregated into one-minute intervals for repeated queries, and it also covers short transactional queries that ACCESS_HISTORY omits. Enterprise Edition or higher, currently a preview feature.

Ask for these four numbers at your next review: is a network policy activated at account scope; how many human users can still authenticate with a password; how many unload parameters are set; what is the Snowsight idle timeout. All four are one query each, and all four are commonly wrong.

What Snowflake Cannot Do — Say This Out Loud

Security teams trust a vendor more after hearing a clean list of limitations. These are real, and pretending otherwise gets found out during implementation.

AskRealityCompensating control
Disable the "Download Results" buttonNo such setting existsRestrict access upstream; cap rows with ROWS_PER_RESULTSET
Cap download row count or file size in the UINot offered as a download limitROWS_PER_RESULTSET at account, user or session — note it limits every query the user runs, not just exports

Sourcing note, stated plainly: the absence of a Snowsight download-limit setting and the ROWS_PER_RESULTSET workaround are documented in a Snowflake Community Knowledge Base article, not in the product documentation. Treat it as a supported workaround with a lower documentation guarantee than the product-doc controls elsewhere in this deck, and re-verify before you build a compliance narrative on it.

Recommended Sequence

Ordered by control strength per unit of effort. Steps 1 and 2 deliver most of the outcome and neither requires an edition change or new spend.

1. Activate a network policy at account scopeRemoves off-network access outright
2. Remove PASSWORD for human users; require IdPMakes Conditional Access unbypassable
3. Turn on device-compliance in the IdPBlocks unmanaged phones at login
4. Apply a session policyShrinks the 18-hour idle window
5. Set the unload parametersCloses bulk export to local disk
6. Add projection policies on regulated columnsMakes legitimate exports harmless
7. Baseline Trust Center and ACCESS_HISTORYProves posture and detects drift

The one-sentence version: Snowflake will not stop a download, so stop the session — activate the network policy you probably already created, force every human through the IdP so device compliance can be enforced, then shorten sessions and close the unload paths behind it.
